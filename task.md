# Задача: свой BPE-токенизатор (Python + Rust)

## 1. Цели

- **Основная:** разобраться, как устроены токенизаторы (обучение словаря, encode/decode).
- **Побочная:** освоить базовый Rust на понятной задаче.

## 2. Что делаем

Byte-level BPE (в духе GPT-2) в четырёх реализациях:

| # | Язык   | Версия    | Назначение                                      |
|---|--------|-----------|-------------------------------------------------|
| 1 | Python | naive     | Эталон корректности, понятная логика            |
| 2 | Python | efficient | Инкрементальное обучение, должно совпасть с #1  |
| 3 | Rust   | naive     | Порт #1, освоение языка на знакомой логике      |
| 4 | Rust   | efficient | Порт #2, бенчмарки                              |

## 3. Что НЕ делаем (non-goals)

- Не пишем WordPiece / Unigram.
- Не дообучаем готовые токенизаторы и не расширяем их словарь.
- Не делаем интеграцию с моделями и HF-совместимость формата (опционально, потом).
- Не оптимизируем под многопоточность, пока нет рабочей однопоточной версии.

## 4. Принятые решения

| Вопрос                    | Решение                                                                 |
|---------------------------|-------------------------------------------------------------------------|
| Пре-токенизация           | Паттерн GPT-2 как есть (`regex` в Python, `fancy-regex` в Rust)         |
| Формат байтов в JSON      | hex                                                                     |
| Размер словаря            | Параметр `vocab_size`; базово 1024 (отладка и сверка всех версий)       |
| Корпус для всех 4 версий  | ~100 МБ (+ маленький срез ~1 МБ для быстрых тестов)                     |
| Корпус побольше           | Позже: 500 МБ / 1 ГБ и больший словарь только для efficient-версий      |
| Структура репозитория     | Монорепозиторий, см. раздел 11                                          |

## 5. Функциональные требования

### 5.1 Обучение
- Вход: текстовый корпус (файл или итератор строк, чтение потоком), `vocab_size`, список специальных токенов.
- Выход: упорядоченный список merges + словарь токенов (id → bytes).
- Базовый алфавит: 256 байт, id 0..255.
- Пре-токенизация: паттерн GPT-2; слияния не пересекают границы слов.
- Корпус сворачивается в словарь «слово → частота» до начала обучения.
- Общий интерфейс обучения для naive и efficient: `train(word_freqs, num_merges) -> merges`.

### 5.2 Encode / Decode
- `encode(text) -> list[int]`: пре-токенизация, затем применение merges по приоритету (порядку обучения).
- `decode(ids) -> str`: конкатенация байтов токенов и декодирование UTF-8 с политикой замены невалидных последовательностей (`errors="replace"` / `from_utf8_lossy`).
- Инвариант: `decode(encode(text)) == text` для любого валидного текста (русский, эмодзи, пробелы, переводы строк).
- Специальные токены (например, `<|endoftext|>`) распознаются в тексте до пре-токенизации и не разбиваются.

### 5.3 Сохранение / загрузка
- Единый JSON-формат для Python и Rust: `vocab` (id → hex), `merges` (список пар id), `special_tokens`, `version`.
- Токенизатор, обученный в одной реализации, должен загружаться и работать в другой.
- Описание формата живёт в `spec/format.md`.

### 5.4 Интерфейс
- Python: класс `Tokenizer` с `train`, `encode`, `decode`, `save`, `load`.
- Rust: библиотека (`lib`) с тем же API + небольшой CLI (`train`, `encode`, `decode`).

## 6. Детерминизм

Результат обучения не должен зависеть от реализации и порядка обхода хеш-таблиц.

- **Выбор пары:** максимальная частота; при равенстве частот выбирается пара с наименьшим `(id_left, id_right)` лексикографически.
- Порядок слов в корпусе не влияет на результат.
- Одинаковый корпус + одинаковые параметры = одинаковые merges во всех четырёх версиях.

## 7. Корректность и тесты

- **Юнит-тесты:** подсчёт пар, одно слияние, encode/decode на коротких примерах, граничные случаи (пустая строка, один символ, неполный UTF-8 при decode, специальные токены).
- **Property-тест:** `decode(encode(x)) == x` на случайных строках.
- **Эквивалентность:** merges #2 == #1, #4 == #3, Python == Rust на одном корпусе (`scripts/compare_merges.py`).
- **Эталон:** сравнить разбиение с `tiktoken` / HF `tokenizers` на небольшом корпусе; допустимы расхождения только из-за разницы в разрешении ничьих, их нужно зафиксировать и объяснить.
- **Золотые файлы** (`spec/golden/`): 3-5 коротких текстов (русский, эмодзи, пробелы, спецтокен) + ожидаемые merges, общие для Python и Rust.

## 8. Данные

- Отладка: `small_1mb.txt` (~1 МБ, например tiny shakespeare или срез русского корпуса).
- Основной корпус: `ru_100mb.txt` (срез русской Википедии), на нём работают все 4 версии.
- Для эксперимента ru/en: английский корпус того же размера.
- Позже (опционально): 500 МБ / 1 ГБ только для efficient-версий.
- Большие файлы в git не коммитятся; в репозитории скрипт загрузки и контрольные суммы.

## 9. Производительность

Метрики:
- время обучения при `vocab_size` 1024 (и больших значениях для efficient-версий);
- пропускная способность `encode` (МБ/с);
- пиковая память при обучении.

Ориентиры (не жёсткие требования):
- efficient заметно быстрее naive на 100 МБ;
- Rust-версии быстрее Python-аналогов.

Инструменты: `pytest-benchmark` / `timeit` для Python, `criterion` для Rust, `bench/run_all.py` для сводной таблицы.

## 10. Эксперимент со словарём

Обучить токенизатор отдельно на русском и английском корпусах и сравнить:
- число токенов на 1000 символов / на параграф параллельного по смыслу текста;
- примеры разбиения слов;
- долю токенов, равных одному байту (показатель того, как плохо словарь покрывает язык).

## 11. Структура репозитория

```
bpe/
├── README.md
├── task.md
├── .gitignore
├── Makefile                 # make test, make bench, make data
│
├── data/                    # в .gitignore, кроме скриптов и README
│   ├── README.md            # откуда корпус, контрольные суммы
│   ├── fetch.py             # скачивание и нарезка (1 МБ, 100 МБ)
│   ├── raw/
│   └── corpus/
│       ├── small_1mb.txt
│       └── ru_100mb.txt
│
├── spec/                    # общий контракт для обеих реализаций
│   ├── format.md            # JSON-формат (hex, версия, поля)
│   ├── pattern.txt          # паттерн пре-токенизации
│   └── golden/              # маленькие корпуса + ожидаемые merges.json
│
├── python/
│   ├── pyproject.toml
│   ├── bpe/
│   │   ├── __init__.py
│   │   ├── pretokenize.py
│   │   ├── naive.py         # версия #1
│   │   ├── fast.py          # версия #2
│   │   ├── tokenizer.py
│   │   └── io.py
│   └── tests/
│
├── rust/
│   ├── Cargo.toml
│   ├── src/
│   │   ├── lib.rs
│   │   ├── pretokenize.rs
│   │   ├── naive.rs         # версия #3
│   │   ├── fast.rs          # версия #4
│   │   ├── tokenizer.rs
│   │   ├── io.rs
│   │   └── bin/main.rs      # CLI: train / encode / decode
│   ├── benches/
│   └── tests/
│
├── bench/
│   ├── run_all.py
│   └── results/
│
├── scripts/
│   └── compare_merges.py
│
└── experiments/
    └── ru_vs_en.py
```

Принципы:
- `spec/` единый источник правды для паттерна, формата и золотых файлов.
- naive и fast с одним интерфейсом `train(...)`, чтобы тесты не зависели от алгоритма.
- Пре-токенизация отдельным модулем: самый хрупкий кусок, тестируется независимо.
- Rust как библиотека + бинарь: библиотека для бенчмарков и возможного PyO3-биндинга.

## 12. Этапы и критерии готовности

0. **Каркас:** структура репозитория, `spec/` (формат, паттерн, золотые файлы), скрипт загрузки данных.
1. **Python naive:** обучение и encode/decode работают, тесты зелёные, сверка с эталоном выполнена.
2. **Python efficient:** merges совпадают с #1 на всех тестовых корпусах, ускорение измерено.
3. **Rust naive:** merges совпадают с Python, JSON-файлы взаимозаменяемы.
4. **Rust efficient:** merges совпадают, бенчмарки собраны, результаты сведены в таблицу.
5. **Эксперимент ru/en** и короткие выводы.

Проект завершён, когда выполнены пункты 1-5 и все тесты на эквивалентность проходят.
